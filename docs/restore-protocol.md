# 恢复（restore）协议

`archive-fixity restore` 从**静态只读副本**重建档案包。副本即载荷根：副本目录内的相对
路径与清单 `path` 一一对应，不做路径重写。单操作者、仅标准库；副本假定静态可信，
不防御核验期间的对抗性并发换文件（与 static 核验模式同一信任边界）。

## 1. 计划文件

`archive-fixity restore --plan plan.json`。计划是 ≤8 MB 的严格 JSON（拒绝重复键、
非有限数值、未定义字段），字段恰好四个：

| 字段 | 含义 |
| --- | --- |
| `manifest` | 可信清单文件路径（相对路径基于计划文件所在目录解析） |
| `replicas` | 副本目录的**有序**数组，1..64 项，不得重复；每个副本目录即一个载荷根 |
| `target` | 最终档案包目录（当前必须不存在，或恰好是本身份此前发布的完整产物） |
| `state` | 私有状态目录，全部暂存与日记账只写在这里 |

路径规则沿用清单：相对路径必须是规范 POSIX 段（无绝对路径、空段、`.`/`..`、反斜杠，
≤128 字符）；绝对路径允许直接使用。计划、清单、副本、目标、状态的任何现存路径段
都不得是符号链接。

## 2. 拓扑约束（启动时强制，违反即失败、不写任何产物）

- `target` 与 `state` 必须在输入树之外。输入树 = 清单所在目录树 + 每个副本目录树
  （即目标/状态不得等于或位于这些目录之内）。
- `target` 与 `state` 必须互不相同、互不包含；计划文件本身也不得位于二者之内。
- 发布要求 `target` 与 `state` 位于同一文件系统（同 `st_dev`），否则失败并保留暂存。

## 3. 清单与容量规则

清单仍为 `{payload_root, entries[path,bytes,sha256]}`，复用核验命令的同一套校验
（`model.validate_entries`）：`sha256` 为 64 位小写十六进制，单文件 0..8 MB，
清单 ≤2000 项，期望总量 ≤32 MB，重复路径拒绝。恢复不使用清单的 `payload_root`
定位副本（副本根由计划给出），但字段仍须通过同一格式校验。

## 4. 选源规则

按清单路径逐项处理，对每个条目按 `replicas` 数组顺序找**第一个合格来源**：

1. `lstat` 后必须是普通文件——缺失、符号链接、FIFO/设备/套接字等一律跳过该副本；
2. 大小必须等于清单 `bytes`；
3. 实读字节的 SHA256 必须等于清单 `sha256`（读取同样受 8 MB 上限约束）。

因此缺失、损坏（同大小异摘要或异大小）、链接或特殊文件都可以由后续副本换源解决；
所有副本都没有合格普通文件时，整个恢复失败，退出 2，不产生目标、不修改任何输入。

## 5. 状态目录布局与日记账

```
<state>/.restore-state/
  journal.json            # 身份 + 已记账条目 + published 标志，原子替换并 fsync
  package/
    payload/<清单相对路径>  # 暂存载荷，目录结构按清单路径建立
    receipts.json         # 逐项来源收据，发布前生成并参与全包重验
```

复制以 65536 字节分块进行，写入字节逐块计数；先写入同目录 `*.part` 临时文件、
fsync 后原子改名到暂存路径。文件**写完并通过字节校验后**才写入日记账；
日记账每次更新都经临时文件 + `os.replace` + 目录 fsync 落盘。中断遗留的 `*.part`
在下次运行开始时清理；未记账的完整暂存文件不被信任，一律删除后重新取源。

## 6. 绑定身份与续跑拒绝

日记账记录的身份为四元组：

```
identity = {
  "manifest_sha256": <清单文件字节 SHA256>,
  "plan_sha256":     <计划文件字节 SHA256>,
  "target":          <目标绝对路径>,
  "replicas":        <有序副本绝对路径数组，顺序参与比较>
}
```

续跑时身份不一致（清单 SHA 变化、目标变化、副本集合或顺序变化、计划字节变化）
直接拒绝：`state identity mismatch ... refusing to resume`，退出 2，状态原样保留。
需要换计划时必须使用新的状态目录。

续跑对日记账中每个已记账条目**重新读取暂存字节做大小+SHA256 校验**，日志本身
永远不能代替字节校验：暂存文件缺失或被篡改则删除该条目记录并重新选源复制。

## 7. 发布、幂等与覆盖拒绝

全部条目记账后，生成 `receipts.json` 并对整个暂存包做发布前重验：

- 暂存普通文件集合必须与清单条目集合完全相等（不多不少，不含链接/特殊文件）；
- 每个暂存文件字节与清单一致；
- 每张收据的字节/摘要与清单一致，且收据来源仍属于计划内副本、当前仍合格。

重验通过后，检查 `target`：

- 不存在：确认同文件系统后 `os.rename` 原子重命名（目标不存在，无覆盖语义），
  再把日记账 `published` 置真并 fsync。
- 已存在且能通过同一套全包重验（含收据来源复核）：识别为本次身份的完整产物，
  补记 `published` 并幂等返回成功——这覆盖“重命名已完成但尚未记账即断电”的窗口。
- 已存在但布局不同、是符号链接、字节/收据不符或重验失败：拒绝覆盖，退出 2，
  目标与输入都不改动。

已记账 `published:true` 且目标完好时重跑，直接识别并幂等成功，不重新复制。

## 8. 失败语义

- 契约/拓扑/身份失败、无合格来源、I/O 失败：退出 2，stderr 说明原因。
- 失败时目标路径绝不出现半成品（所有写入只发生在状态目录；发布是单次同盘改名）。
- 输入（清单、计划、副本）只读打开，恢复流程不创建、不修改、不删除其中任何条目。
- 恢复状态不丢失：失败后状态目录保留日记账与暂存，修正环境后用同一计划续跑。

## 9. 收据格式

`receipts.json` 是按清单路径排序的数组，每项：

```json
{
  "path": "sub/b.bin",
  "bytes": 1500,
  "sha256": "<清单摘要，即实际字节摘要>",
  "source": {
    "index": 1,
    "root": "/abs/replica1",
    "path": "/abs/replica1/sub/b.bin",
    "bytes": 1500,
    "sha256": "<来源实读摘要>"
  }
}
```

`source.index` 是命中的副本在计划中的序号（0 起），可据此审计每个文件实际取自
哪个副本；摘要与字节数同时给出，收据可独立复核。

## 10. 崩溃点与测试方法

进程内屏障回调（测试用，非 CLI 面）在确定节点抛异常模拟崩溃，子进程辅助脚本
`tests/restore_crash.py` 产生真实磁盘中断状态，再用正式 CLI 续跑：

| 故障点 | 模拟方式 | 续跑断言 |
| --- | --- | --- |
| 复制中 | `copy_chunk` 屏障，首块写入后中断 | 无目标、无记账；`.part` 被清理，重新复制，字节与收据齐全 |
| 文件写完未记账 | `file_unjournaled` 屏障 | 暂存完整但日记账无记录；续跑删除残留并重新取源 |
| 发布未记账 | `publish_unjournaled` 屏障（改名后、记账前） | 目标已是完整包；续跑识别本身份产物、补记账，幂等成功 |
| 暂存篡改 | 记账后改写暂存字节 | 续跑字节重验失败，丢弃篡改文件并重新选源（可落到其他副本） |
| 身份冲突 | 续跑前改清单/目标/副本顺序 | 拒绝续跑，状态保留 |
| 无合格来源 | 全部副本均不匹配 | 失败退出 2，无目标、输入字节不变、状态保留 |

## 11. CLI 摘要

成功时 stdout 输出 JSON 摘要（退出 0）：

```json
{
  "schema_version": 1,
  "identity": { "...": "见第 6 节" },
  "target": "/abs/target/package",
  "files": 3,
  "bytes": 20034,
  "receipts": [ "...逐项收据..." ],
  "resumed": false,
  "recognized_existing": false
}
```

`resumed:true` 表示状态目录中已存在日记账；`recognized_existing:true` 表示目标处的
完整产物被识别为本次身份的既有成果（含发布未记账窗口与幂等重跑）。
历史平面命令 `archive-fixity --source ... --output ...` 的行为与输出保持不变。
